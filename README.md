# Веб-отчётность — учёт аварий на базовых станциях (кейс №02, «Мотив»)

Веб-приложение для ведения отчётности по авариям на базовых станциях сотовой сети:
регистрация аварий, отчётность с фильтрами и выгрузкой, статистика, роли доступа.

**Стек:** Python 3.11 (Flask + gunicorn) на Debian bookworm, **MariaDB 10.1** в Docker,
Docker Compose. Интерфейс без внешних CDN, совместим с Chrome 75.

---

## 🚀 Быстрый старт (для проверки)

**Нужен только [Docker Desktop](https://www.docker.com/products/docker-desktop/)** (с Docker Compose). Python/БД ставить не нужно — всё в контейнерах.

1. Запустить Docker Desktop.
2. В папке проекта выполнить:
   ```bash
   docker compose up -d --build
   ```
   (первый запуск — 1–2 минуты: собирается образ и поднимается MariaDB 10.1.)
3. Открыть в браузере: **http://localhost** (порт 80; с другого компьютера — `http://<IP-сервера>`)
4. Войти: логин **`admin`**, пароль **`admin`**.
5. (по желанию) наполнить демо-данными — см. раздел «Демо-данные» ниже.

**Остановить:**
```bash
docker compose down          # остановить (данные сохраняются)
docker compose down -v       # остановить и удалить данные (чистый сброс)
```

**Проверить логи, если что-то не поднялось:**
```bash
docker compose logs app --tail 50
docker compose ps
```

**Если порт 80 занят** (ошибка `port is already allocated` / `address already in use`) —
запустить на другом порте и открыть http://localhost:8080:
```bash
APP_PORT=8080 docker compose up -d --build
```
Если занят порт 3306 (на машине уже стоит MySQL/MariaDB) — остановить локальную СУБД
(`sudo systemctl stop mysql` / `mariadb`), т.к. по ТЗ база должна вещать на 3306.

## Демо-данные

Справочник БС заполняется автоматически при старте. Тестовые аварии:
```bash
docker compose exec app python seed.py          # добавить ~36 демо-аварий
docker compose exec app python seed.py --reset  # сначала очистить аварии
```

Либо загрузить аварии через веб: «Отчётность» → «↑ Импорт CSV» (формат — как у выгрузки).

## Возможности

- **Аварии.** Форма из 19 полей ТЗ (4 блока). Справочники для фиксированных полей, календарь для
  времени, галочка «НВ». Длительность и общее время простоя БС считаются автоматически во время
  ввода. Поле «Тип объекта» (станция / контроллер / узел…) — авария может затрагивать вышестоящий
  объект, за которым N станций.
- **Скоростной ввод дежурного.** Автозаполнение из справочника БС, шаблоны типовых аварий,
  «дублировать последнюю», `Ctrl+Enter`. **Групповое заведение** (одна авария сразу на много
  станций) и **групповое закрытие**. Памятка — `/guide` и [МЕТОДИЧКА_ДЕЖУРНОГО.md](МЕТОДИЧКА_ДЕЖУРНОГО.md).
- **Отчётность.** Период + фильтры (направление, ТЦ, категория, тип сети, проблема, статус, поиск),
  быстрые периоды и «проблемы», редактирование и быстрое закрытие строки, **выгрузка и импорт CSV**.
- **Статистика.** Отдельная вкладка: период (24 часа / неделя / месяц / год / свой), открыто/закрыто,
  затронуто БС, суммарный и средний простой, разрезы по категориям/типам/направлениям/ТЦ/сети и
  топ станций — всё по реальным записям БД.
- **Станции.** Справочник БС и история поломок по каждой станции (таймлайн).
- **Роли и пользователи.** Владелец / администратор / дежурный / инженер — см. [РОЛИ_И_ПРАВА.md](РОЛИ_И_ПРАВА.md).
  Управление пользователями, смена своего пароля, журнал действий.

## Принятые допущения

Каждое допущение продублировано вопросом эксперту в [ВОПРОСЫ_К_СОЗВОНУ.md](ВОПРОСЫ_К_СОЗВОНУ.md).
- Добавлен первичный ключ `ID`; остальные поля — по именам из ТЗ.
- «НВ» хранится в `END_TIME` как `0000-00-00 00:00:00`.
- «С» (сектор) хранится в `NUMB_RBS` как `0`; при расчёте простоя считается как 1 БС.
- `PROSTOY` и `COMMON_PROSTOY` хранятся строкой `чч.мм.сс` (ограничение типа `TIME` 838 ч снято по
  согласованию с экспертом) — длинные простои не теряются.
- Служебные nullable-поля: `STATION_CODE` (связь со справочником БС) и `OBJ_TYPE` (тип объекта).
- Логотип в интерфейсе — **нейтральная заглушка**; официальный логотип «Мотива» положите в
  `app/static/` (вопрос №76 эксперту).

## Структура проекта

```
docker-compose.yml       оркестрация: app + MariaDB 10.1
.env.example             шаблон переменных (секреты в репозиторий не кладём)
db/init.sql              схема БД
app/
  app.py                 сервер: маршруты, права, расчёты
  database.py            работа с MariaDB: подключение, запросы, настройка схемы
  Dockerfile             образ приложения (Debian bookworm)
  requirements.txt       зависимости Python
  templates/             HTML-шаблоны
  static/                style.css, app.js, logo-mark.svg
  tests.py               юнит-тесты
  seed.py                демо-данные
import_svodka.py         импорт реальной Excel-сводки (запуск на хосте)
```

**Переменные окружения** (`.env`, по образцу [.env.example](.env.example)):
`DB_ROOT_PASSWORD`, `DB_USER`, `DB_PASSWORD`, `SECRET_KEY`, `ADMIN_LOGIN`, `ADMIN_PASSWORD`,
`TZ`, `APP_PORT`, `COOKIE_SECURE`. Без `.env` используются безопасные значения по умолчанию.

## Тесты и безопасность

Юнит-тесты (время, расчёты, валидация формы):
```bash
docker compose exec -e SKIP_BOOTSTRAP=1 app python -m unittest tests -v
```

Меры безопасности: CSRF на всех POST (включая вход), `HttpOnly`/`SameSite` cookie, запуск
контейнера от непривилегированного пользователя, `.dockerignore`,
экранирование формул в CSV, проверка прав на сервере. Разбор внешнего аудита (57 пунктов) —
в [ОТВЕТ_РЕЕСТР_ПРОБЛЕМ.md](ОТВЕТ_РЕЕСТР_ПРОБЛЕМ.md).
